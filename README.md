## Решение 1

Для организации хранения исходного кода и процессов CI/CD предлагается использовать облачную платформу **GitLab.com** совместно со встроенной системой **GitLab CI/CD**.

GitLab объединяет систему управления Git-репозиториями, CI/CD, управление переменными и секретами, Container Registry и механизм GitLab Runner. Благодаря этому основные требования можно реализовать в рамках одной платформы без необходимости интеграции нескольких независимых продуктов.

### Соответствие требованиям

| Требование | Реализация в GitLab |
| --- | --- |
| Облачная система | GitLab доступен в виде облачного сервиса GitLab.com |
| Система контроля версий Git | Git является основной системой контроля версий GitLab |
| Репозиторий на каждый сервис | Для каждого микросервиса можно создать отдельный GitLab Project с собственным Git-репозиторием |
| Запуск сборки по событию из системы контроля версий | GitLab CI/CD позволяет автоматически запускать pipeline при `push`, создании Merge Request, появлении тега и других событиях |
| Запуск сборки по кнопке с указанием параметров | Pipeline можно запустить вручную из интерфейса GitLab, передав необходимые CI/CD variables |
| Возможность привязать настройки к каждой сборке | Конфигурация pipeline хранится вместе с исходным кодом в `.gitlab-ci.yml`, а условия выполнения и переменные позволяют задавать необходимые настройки сборки |
| Возможность создания шаблонов для различных конфигураций сборок | GitLab CI/CD поддерживает повторное использование конфигурации и подключение других YAML-файлов с помощью `include`, что позволяет создавать общие шаблоны pipeline |
| Возможность безопасного хранения секретных данных | Для хранения паролей, токенов и других чувствительных данных используются CI/CD variables. Для них можно настроить маскирование и ограничение использования защищёнными ветками и тегами |
| Несколько конфигураций для сборки из одного репозитория | В одном `.gitlab-ci.yml` можно описать несколько jobs и различные условия их запуска с помощью `rules`, переменных и подключаемых конфигураций |
| Кастомные шаги при сборке | В секции `script` каждого job можно выполнять необходимые команды и пользовательские скрипты |
| Собственные Docker-образы для сборки | GitLab Runner с Docker executor позволяет выполнять jobs в заданных Docker-образах. Собственные образы можно хранить в GitLab Container Registry |
| Агенты сборки на собственных серверах | GitLab поддерживает self-managed GitLab Runner, который можно установить на собственные физические или виртуальные серверы |
| Возможность параллельного запуска нескольких сборок | GitLab Runner позволяет одновременно выполнять несколько jobs и pipelines при наличии доступных runners. Количество одновременно выполняемых задач определяется конфигурацией runners |
| Возможность параллельного запуска тестов | GitLab CI/CD позволяет разделить тесты между несколькими параллельными jobs. Для дополнительного распараллеливания поддерживаются `parallel` и `parallel:matrix` |

### Схема взаимодействия компонентов

```text
Разработчик
    |
    | git push / merge request
    v
GitLab.com
    |
    +-- Git Repository
    |
    +-- GitLab CI/CD
           |
           | создаёт Pipeline
           v
       GitLab Runner
       /          \
      /            \
Hosted Runner    Self-managed Runner
      \            /
       \          /
        v        v
     Build / Tests
           |
           v
      Docker Image
           |
           v
GitLab Container Registry
           |
           v
        Deploy
           |
           v
   Целевая среда
```

Для каждого микросервиса создаётся отдельный GitLab Project и Git-репозиторий. Разработчик вносит изменения и отправляет их в GitLab. В зависимости от заданных правил событие `push`, Merge Request, создание тега или ручной запуск инициирует GitLab CI/CD pipeline.

Pipeline состоит из отдельных jobs, например сборки приложения, запуска автоматических тестов, создания Docker-образа и развёртывания. Jobs передаются доступным GitLab Runner. Для выполнения сборок можно использовать как предоставляемые GitLab облачные runners, так и self-managed runners, установленные на собственной инфраструктуре.

Параметры окружения и секретные данные передаются в jobs через CI/CD variables и не должны храниться непосредственно в исходном коде. Для контейнеризированных приложений собранные Docker-образы могут сохраняться в GitLab Container Registry, после чего использоваться при развёртывании приложения.

Таким образом, связка **GitLab.com + GitLab CI/CD + GitLab Runner + GitLab Container Registry** удовлетворяет перечисленным требованиям и предоставляет единую платформу для хранения исходного кода, автоматической сборки, тестирования и последующего развёртывания микросервисов.

## Решение 2

Для централизованного сбора, хранения и анализа логов предлагается использовать связку **Vector + Elasticsearch + Kibana**.

В данной архитектуре каждый компонент выполняет отдельную функцию:

- **Vector** — собирает логи с хостов, обрабатывает их и передаёт в центральное хранилище;
- **Elasticsearch** — обеспечивает централизованное хранение, индексирование, поиск и фильтрацию логов;
- **Kibana** — предоставляет разработчикам веб-интерфейс для поиска, анализа и просмотра логов.

Такое разделение позволяет не встраивать работу с централизованной системой логирования непосредственно в приложения. Сервисы могут записывать журнальные сообщения в стандартный поток `stdout`, после чего инфраструктура логирования самостоятельно выполняет их сбор и доставку.

### Соответствие требованиям

| Требование | Реализация |
| --- | --- |
| Сбор логов в центральное хранилище со всех хостов | Vector устанавливается на хостах, обслуживающих систему, собирает журнальные события и отправляет их в централизованный Elasticsearch |
| Минимальные требования к приложениям, сбор логов из `stdout` | Приложения могут записывать логи в стандартный поток `stdout`. Vector может получать журнальные события из соответствующего источника, например логов контейнеров, без необходимости добавлять в приложение собственную интеграцию с Elasticsearch |
| Гарантированная доставка логов до центрального хранилища | Vector поддерживает буферизацию событий и повторные попытки отправки при временной недоступности получателя. Для повышения надёжности может использоваться дисковый буфер, позволяющий временно сохранять события на хосте до восстановления доступности Elasticsearch |
| Поиск и фильтрация по записям логов | Elasticsearch индексирует поступающие события и предоставляет возможности поиска и фильтрации по времени, сервису, хосту, уровню события и другим полям |
| Пользовательский интерфейс с доступом для разработчиков | Kibana предоставляет веб-интерфейс для работы с данными Elasticsearch, через который разработчики могут просматривать, искать и анализировать журнальные события |
| Возможность дать ссылку на сохранённый поиск | В Kibana можно сохранять настроенные представления и поисковые запросы и предоставлять другим пользователям доступ к соответствующему представлению или ссылке при наличии необходимых прав |

### Схема взаимодействия компонентов

```text
Микросервисы
     |
     | stdout / stderr
     v
Контейнеры / файлы логов
     |
     v
Vector
     |
     | сбор
     | обработка
     | буферизация
     | повторная отправка при ошибках
     v
Elasticsearch
     |
     | централизованное хранение
     | индексирование
     | поиск и фильтрация
     v
Kibana
     |
     +--> просмотр логов
     +--> поиск и фильтрация
     +--> сохранённые представления
     +--> доступ разработчиков
```

### Принцип работы

Микросервисы записывают журнальные сообщения в стандартные потоки `stdout` и `stderr`. Благодаря этому приложениям не требуется знать, где расположено центральное хранилище логов или каким способом данные будут в него доставлены.

На хостах размещается **Vector**, который получает журнальные события от соответствующих источников, при необходимости преобразует и дополняет их метаданными, после чего отправляет в **Elasticsearch**.

Для повышения надёжности доставки Vector может использовать буферизацию. Если Elasticsearch временно недоступен, события сохраняются в буфере и выполняются повторные попытки их передачи. Использование дискового буфера позволяет снизить вероятность потери логов при временных проблемах сети или недоступности центрального хранилища.

**Elasticsearch** выступает централизованным хранилищем логов. Полученные события индексируются, что позволяет выполнять поиск и фильтрацию по различным параметрам, например времени события, имени микросервиса, хосту или уровню журналирования.

Для работы пользователей с журналами используется **Kibana**. Разработчики получают единый веб-интерфейс, через который могут находить необходимые события, применять фильтры и сохранять полезные представления для дальнейшего использования и совместной работы.

Таким образом, связка **Vector + Elasticsearch + Kibana** обеспечивает централизованный сбор и анализ логов микросервисной системы, позволяет приложениям ограничиться записью логов в стандартные потоки, предоставляет механизмы надёжной доставки и буферизации, а также обеспечивает разработчиков средствами поиска и удобным пользовательским интерфейсом.



## Задание 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

## Решение 3

Для централизованного мониторинга инфраструктуры и микросервисов предлагается использовать связку **Prometheus + node_exporter + cAdvisor + Grafana**.

В данной архитектуре компоненты выполняют следующие функции:

- **node_exporter** — предоставляет Prometheus системные метрики хостов;
- **cAdvisor** — предоставляет метрики использования ресурсов контейнерами;
- **микросервисы** — предоставляют собственные прикладные метрики через endpoint `/metrics`;
- **Prometheus** — централизованно собирает и хранит метрики и предоставляет язык запросов PromQL;
- **Grafana** — предоставляет пользовательский интерфейс для анализа и визуализации собранных метрик.

Такой подход позволяет разделить инфраструктурные, контейнерные и прикладные метрики, сохраняя их в единой системе мониторинга.

### Соответствие требованиям

| Требование | Реализация |
| --- | --- |
| Сбор метрик со всех хостов | На обслуживающих систему хостах запускается node_exporter, а Prometheus периодически опрашивает его HTTP endpoint и собирает системные метрики |
| Метрики состояния ресурсов хостов: CPU, RAM, HDD, Network | node_exporter предоставляет информацию о загрузке процессора, использовании оперативной памяти, файловых системах, дисковой и сетевой активности |
| Метрики потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network | Для контейнеризированных микросервисов cAdvisor собирает сведения об использовании CPU, памяти, файловой системы и сети отдельными контейнерами |
| Метрики, специфичные для каждого сервиса | Микросервисы могут предоставлять собственный endpoint `/metrics` с прикладными показателями, например количеством запросов, временем их обработки, количеством ошибок и другими специфичными для приложения метриками |
| Пользовательский интерфейс с возможностью делать запросы и агрегировать информацию | Prometheus предоставляет язык PromQL для запросов и агрегации временных рядов. Запросы к Prometheus также могут выполняться через интерфейс Grafana |
| Пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы | Grafana позволяет создавать dashboards с графиками, таблицами и другими панелями, используя Prometheus в качестве источника данных |

### Схема взаимодействия компонентов

```text
Хосты
  |
  +--> node_exporter
  |       |
  |       +--> CPU
  |       +--> RAM
  |       +--> HDD
  |       +--> Network
  |
  +--> cAdvisor
  |       |
  |       +--> CPU контейнеров
  |       +--> RAM контейнеров
  |       +--> Filesystem контейнеров
  |       +--> Network контейнеров
  |
Микросервисы
  |
  +--> /metrics
         |
         +--> количество запросов
         +--> время обработки
         +--> ошибки
         +--> другие прикладные метрики

              |
              v
         Prometheus
              |
              | сбор метрик
              | хранение временных рядов
              | PromQL
              | агрегация
              v
           Grafana
              |
              +--> dashboards
              +--> графики
              +--> таблицы
              +--> запросы
```

### Принцип работы

На каждом хосте запускается **node_exporter**, который предоставляет системные метрики операционной системы. Prometheus периодически обращается к exporter и сохраняет полученные показатели в своей базе временных рядов. Таким образом собирается информация о состоянии CPU, оперативной памяти, дисковых ресурсов и сети хостов.

Для получения информации о потреблении ресурсов отдельными контейнеризированными микросервисами используется **cAdvisor**. Он предоставляет метрики использования CPU, памяти, файловой системы и сети для отдельных контейнеров, которые также собираются Prometheus.

Прикладные показатели предоставляются непосредственно микросервисами через endpoint `/metrics`. Это позволяет собирать специфичные для конкретного приложения метрики, например количество обработанных HTTP-запросов, время обработки запросов, число ошибок или другие показатели, характеризующие работу сервиса.

**Prometheus** выполняет централизованный сбор и хранение полученных временных рядов. С помощью языка **PromQL** можно выполнять запросы, фильтрацию и агрегацию метрик, например вычислять среднюю загрузку CPU, скорость изменения счётчиков запросов или долю запросов, завершившихся ошибкой.

Для визуализации используется **Grafana**, в которой Prometheus настраивается в качестве источника данных. Grafana позволяет создавать различные dashboards и панели для отображения состояния инфраструктуры и приложений. На одном dashboard можно объединить системные показатели хостов, использование ресурсов отдельными микросервисами и прикладные показатели.

Таким образом, связка **node_exporter + cAdvisor + Prometheus + Grafana** обеспечивает централизованный мониторинг как инфраструктуры, так и работающих на ней микросервисов. Она позволяет собирать системные, контейнерные и прикладные метрики, выполнять запросы и агрегацию данных и создавать панели для контроля состояния всей системы.
