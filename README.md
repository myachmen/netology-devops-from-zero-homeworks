## Решение 1

Минимальный набор метрик:

1. ```CPU utilization / Load Average``` — позволяет контролировать загрузку процессора, поскольку основная работа платформы связана с вычислениями. Высокая загрузка CPU может приводить к увеличению времени выполнения задач.
2. ```RAM utilization``` — позволяет контролировать использование оперативной памяти и своевременно обнаруживать её нехватку.
3. ```Свободное место на диске``` — платформа сохраняет текстовые отчёты на диск, поэтому заполнение файловой системы может привести к невозможности сохранения новых отчётов.
4. ```Количество свободных inode``` — даже при наличии свободного дискового пространства создание новых файлов станет невозможным, если закончатся inode.
5. ```HTTP-коды ответов``` — количество и доля ответов 2xx, 4xx, 5xx позволяют оценивать доступность сервиса и количество ошибок.
6. ```Время ответа HTTP (latency)``` — позволяет контролировать скорость ответа платформы пользователям.
7. ```Количество HTTP-запросов (request rate)``` — позволяет оценивать текущую нагрузку на сервис.

Таким образом, данный набор позволяет контролировать как состояние инфраструктуры (CPU, RAM, диск, inode), так и состояние самого сервиса с точки зрения клиента (HTTP-коды, время ответа и количество запросов).

## Решение 2

Для менеджера продукта технические метрики инфраструктуры стоит дополнить показателями, непосредственно характеризующими качество работы сервиса для пользователя.

Можно использовать следующие показатели:

1. ```Доступность сервиса``` — доля времени, в течение которого платформа доступна пользователям.
2. ```Доля успешных запросов``` — отношение успешно обработанных HTTP-запросов к общему количеству запросов.
3. ```Время ответа сервиса``` — например, доля запросов, обработанных быстрее заданного времени.
4. ```Время формирования отчёта``` — поскольку основная функция платформы заключается в выполнении вычислений и создании отчётов, этот показатель непосредственно отражает качество работы сервиса для клиента.

Для формализации требований можно использовать понятия:

1. ```SLI (Service Level Indicator)``` — фактически измеряемый показатель качества работы сервиса. Например, доступность за месяц составила 99,95%, а 97% запросов были обработаны быстрее 500 мс.
2. ```SLO (Service Level Objective)``` — целевое значение SLI. Например: доступность сервиса должна быть не менее 99,9% в месяц или 95% HTTP-запросов должны выполняться быстрее 500 мс.
3. ```SLA (Service Level Agreement)``` — соглашение об уровне предоставления сервиса между поставщиком и потребителем. Оно может содержать несколько SLO и определять последствия их нарушения.

Например, для данной платформы можно установить SLO: не менее 99,9% успешных запросов за месяц, а фактически измеренную долю успешных запросов использовать как SLI. На основе этого показателя можно контролировать выполнение принятого SLA.

## Задание 9

Изучите список [telegraf inputs](https://github.com/influxdata/telegraf/tree/master/plugins/inputs). 
Добавьте в конфигурацию telegraf следующий плагин - [docker](https://github.com/influxdata/telegraf/tree/master/plugins/inputs/docker):
```
[[inputs.docker]]
  endpoint = "unix:///var/run/docker.sock"
```

Дополнительно вам может потребоваться донастройка контейнера telegraf в `docker-compose.yml` дополнительного volume и 
режима privileged:
```
  telegraf:
    image: telegraf:1.4.0
    privileged: true
    volumes:
      - ./etc/telegraf.conf:/etc/telegraf/telegraf.conf:Z
      - /var/run/docker.sock:/var/run/docker.sock:Z
    links:
      - influxdb
    ports:
      - "8092:8092/udp"
      - "8094:8094"
      - "8125:8125/udp"
```

После настройке перезапустите telegraf, обновите веб интерфейс и приведите скриншотом список `measurments` в 
веб-интерфейсе базы telegraf.autogen . Там должны появиться метрики, связанные с docker.

Факультативно можете изучить какие метрики собирает telegraf после выполнения данного задания.

## Решение 9

В актуальной версии репозитория ```influxdata/sandbox``` плагин ```inputs.docker```, указанный в задании, уже присутствует в конфигурационном файле ```telegraf/telegraf.conf```. 
Также в ```docker-compose.yml``` уже настроено подключение ```/var/run/docker.sock``` к контейнеру Telegraf. Поэтому дополнительное добавление плагина и изменение ```docker-compose.yml``` не потребовались.

После запуска Telegraf в Chronograf автоматически появились Docker-метрики (```docker```, ```docker_container_cpu```, ```docker_container_mem```, ```docker_container_net```, ```docker_container_blkio```, ```docker_container_status```), что подтверждает корректную работу плагина inputs.docker:

![img](img/image10.png)

При запуске контейнера Telegraf была выявлена несовместимость конфигурации из репозитория с используемой актуальной версией Telegraf 1.39.3. Параметры ```container_names```, ```perdevice``` и ```total``` плагина ```inputs.docker``` больше не поддерживаются данной версией и приводили к завершению контейнера с ошибкой. 
Устаревшие параметры были удалены из ```telegraf/telegraf.conf```, после чего контейнер Telegraf успешно запустился и начал передавать Docker-метрики в InfluxDB.
