## Задание 1: API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:

- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

## Решение 1

Для организации доступа к микросервисам через единую точку входа рассмотрены три решения: **NGINX**, **Kong Gateway** и **Traefik**.

Все рассматриваемые решения позволяют выполнить основные требования задачи: маршрутизацию запросов, проверку аутентификационной информации и HTTPS termination. При этом продукты отличаются своим основным назначением и подходом к реализации функций API Gateway.

| Критерий | NGINX | Kong Gateway | Traefik |
|---|---|---|---|
| Маршрутизация запросов | Да. Маршрутизация настраивается с помощью `location`, `proxy_pass` и других директив | Да. Используются сущности Service и Route, поддерживается маршрутизация по host, path, HTTP-методу, headers и другим параметрам | Да. Используются Routers и Services, поддерживаются правила на основе Host, Path, Headers и других параметров |
| Проверка аутентификации | Да. Поддерживается Basic Authentication, а также передача проверки внешнему сервису через `auth_request` | Да. Поддерживаются различные механизмы аутентификации через плагины, например Basic Auth, Key Authentication, OAuth 2.0, LDAP и другие | Да. Поддерживается Basic Authentication и передача проверки внешнему сервису через middleware `ForwardAuth` |
| HTTPS termination | Да | Да | Да |
| Работа с внешним сервисом аутентификации | Да, через `auth_request` | Да, возможно использование плагинов и внешних сервисов | Да, через `ForwardAuth` |
| Динамическое обнаружение сервисов | Ограничено по сравнению с cloud-native решениями, обычно требуется явная конфигурация или дополнительные механизмы | Да, хорошо подходит для динамической микросервисной инфраструктуры | Да, одна из сильных сторон Traefik; есть интеграция с Docker, Kubernetes и другими providers |
| Расширяемость | Высокая, но дополнительную функциональность часто требуется реализовывать конфигурацией или дополнительными модулями | Высокая. Большое количество плагинов для аутентификации, ограничения запросов, логирования и другой API-функциональности | Высокая. Дополнительная обработка запросов реализуется с помощью middleware |
| Основное назначение | Web-сервер, reverse proxy и load balancer | API Gateway | Application proxy / cloud-native reverse proxy |
| Сложность эксплуатации | Относительно низкая для простых конфигураций | Средняя, продукт имеет больше специализированных возможностей | Относительно низкая, особенно в контейнерной инфраструктуре |

### Выбор решения

Для поставленной задачи я бы выбрал **Kong Gateway**.

Все три рассмотренных решения удовлетворяют обязательным требованиям: поддерживают маршрутизацию запросов, позволяют организовать проверку аутентификации и могут выполнять HTTPS termination.

NGINX является зрелым и широко используемым reverse proxy и позволяет реализовать необходимые функции API Gateway, однако значительная часть такой функциональности строится с помощью его конфигурации и дополнительных механизмов.

Traefik хорошо подходит для динамической контейнерной инфраструктуры благодаря автоматическому обнаружению сервисов и интеграции с Docker и Kubernetes. Он также предоставляет необходимые возможности маршрутизации, TLS и аутентификации.

Kong Gateway изначально предназначен для использования в качестве API Gateway и предоставляет специализированные механизмы маршрутизации, аутентификации и расширения функциональности с помощью плагинов. Это позволяет централизованно решать типичные задачи API Gateway и уменьшает необходимость реализации этих механизмов непосредственно в микросервисах.

Поэтому из рассмотренных вариантов **Kong Gateway наиболее полно соответствует поставленной задаче** и является предпочтительным решением для использования в качестве API Gateway.

## Задание 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:

- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

## Решение 2

Для организации обмена сообщениями между микросервисами рассмотрены три решения: **RabbitMQ**, **Apache Kafka** и **NATS JetStream**.

Все рассматриваемые решения позволяют организовать надёжный обмен сообщениями между микросервисами, однако отличаются архитектурой, основными сценариями использования и сложностью эксплуатации.

| Критерий | RabbitMQ | Apache Kafka | NATS JetStream |
|---|---|---|---|
| Кластеризация | Да. Поддерживает объединение нескольких узлов в кластер | Да. Изначально рассчитана на работу в распределённом кластере | Да. JetStream может работать в составе кластера NATS |
| Репликация сообщений | Да. Для высокой доступности могут использоваться Quorum Queues | Да. Партиции топиков могут иметь несколько реплик на разных брокерах | Да. Streams могут иметь несколько реплик на разных узлах |
| Хранение сообщений на диске | Да. Поддерживаются durable queues и persistent messages | Да. Сообщения сохраняются в журнале на диске в соответствии с политикой хранения | Да. Для Streams доступен тип хранения File Storage |
| Высокая производительность | Да. Подходит для большинства задач обмена сообщениями | Да. Высокая пропускная способность является одной из сильных сторон Kafka | Да. NATS ориентирован на высокопроизводительный обмен сообщениями |
| Различные форматы сообщений | Да. Формат полезной нагрузки определяется приложением | Да. Возможна передача JSON, Avro, Protobuf и других форматов | Да. Полезная нагрузка передаётся в виде байтов, формат определяется приложением |
| Разграничение доступа | Да. Поддерживаются пользователи, Virtual Hosts и permissions | Да. Используются ACL для управления доступом к topics и другим ресурсам | Да. Можно ограничивать права publish и subscribe для отдельных subjects |
| Повторное чтение сообщений | Возможно в зависимости от используемой модели и конфигурации | Да. Consumer может повторно читать сохранённые события, изменяя offset | Да. JetStream поддерживает сохранение и повторное получение сообщений |
| Поддержка классических очередей сообщений | Да. Один из основных сценариев использования | Не является основной моделью работы | Да |
| Потоковая обработка событий | Возможна, но не является основным назначением | Да. Один из основных сценариев использования Kafka | Да |
| Простота эксплуатации | Относительно высокая. Имеется Management UI и зрелые средства администрирования | Ниже по сравнению с другими рассматриваемыми решениями из-за более сложной распределённой архитектуры | Относительно высокая, архитектура NATS достаточно лёгкая |
| Основное назначение | Классический message broker, очереди и маршрутизация сообщений | Распределённая event streaming platform | Высокопроизводительный messaging с возможностью персистентного хранения через JetStream |

### Выбор решения

Для поставленной задачи я бы выбрал **RabbitMQ**.

Все три рассмотренных решения удовлетворяют основным требованиям задачи: поддерживают кластеризацию, позволяют хранить сообщения на диске, обеспечивают высокую производительность, позволяют передавать сообщения различных форматов и имеют механизмы разграничения доступа.

**Apache Kafka** особенно хорошо подходит для систем с очень большим потоком событий, распределённой потоковой обработки и сценариев, в которых требуется длительное хранение и повторное чтение событий. При этом её архитектура сложнее в эксплуатации и для обычного обмена сообщениями между микросервисами часть возможностей Kafka может оказаться избыточной.

**NATS JetStream** является лёгким и высокопроизводительным решением. JetStream добавляет к NATS персистентное хранение, репликацию и повторное получение сообщений. Это делает его подходящим для современной микросервисной инфраструктуры, особенно когда важны производительность и сравнительно простая архитектура.

**RabbitMQ** является специализированным брокером сообщений и предоставляет развитые механизмы очередей, маршрутизации, подтверждения доставки, персистентного хранения и разграничения доступа. При этом RabbitMQ имеет зрелые инструменты администрирования и относительно понятную модель эксплуатации.

Таким образом, для поставленной задачи **RabbitMQ является наиболее сбалансированным решением**. Он выполняет все обязательные требования и при этом обеспечивает сравнительно простую эксплуатацию, которая отдельно указана в условиях задачи.
