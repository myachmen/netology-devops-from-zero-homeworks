## Задание 1. Необходимо определить требуемые ресурсы

Известно, что проекту нужны база данных, система кеширования, а само приложение состоит из бекенда и фронтенда. Опишите, какие ресурсы нужны, если известно:

1. Необходимо упаковать приложение в чарт для деплоя в разные окружения. 
2. База данных должна быть отказоустойчивой. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
3. Кеш должен быть отказоустойчивый. Потребляет 4 ГБ ОЗУ в работе, 1 ядро. 3 копии. 
4. Фронтенд обрабатывает внешние запросы быстро, отдавая статику. Потребляет не более 50 МБ ОЗУ на каждый экземпляр, 0.2 ядра. 5 копий. 
5. Бекенд потребляет 600 МБ ОЗУ и по 1 ядру на копию. 10 копий.

## Решение 1

### 1. Расчёт ресурсов приложения

Исходные требования к компонентам:

| Компонент | Реплики | CPU на реплику | RAM на реплику | CPU всего | RAM всего |
|---|---:|---:|---:|---:|---:|
| База данных | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Кеш | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| Frontend | 5 | 0,2 | 50 МБ | 1 | 0,25 ГБ |
| Backend | 10 | 1 | 600 МБ | 10 | 6 ГБ |
| **Итого** | **21** | | | **17** | **30,25 ГБ** |

Расчёт производится по формулам:

- CPU = количество реплик × CPU на реплику.
- RAM = количество реплик × RAM на реплику.

Для расчётов используются десятичные единицы: 1 ГБ = 1000 МБ.

**Минимальная потребность приложения составляет 17 CPU и 30,25 ГБ RAM.**

Полученные значения не учитывают служебные процессы Kubernetes, операционную систему и резервирование ресурсов.

### 2. Выбор конфигурации рабочих нод

Рассмотрим несколько вариантов конфигурации Worker Nodes.

| Конфигурация ноды | Минимум нод по CPU | Минимум нод по RAM | Минимальное количество |
|---|---:|---:|---:|
| 4 vCPU / 8 ГБ | 5 | 4 | 5 |
| 8 vCPU / 16 ГБ | 3 | 2 | 3 |
| 8 vCPU / 32 ГБ | 3 | 1 | 3 |

В таблице приведены арифметические минимумы без учёта служебных ресурсов, отказоустойчивости и ограничений размещения отдельных Pod.

В качестве базовой конфигурации выбраны **Worker Nodes с 8 vCPU и 16 ГБ RAM**.

Такая конфигурация позволяет распределить реплики приложения между несколькими нодами и предусмотреть резерв ресурсов на случай отказа одного узла.

### 3. Обеспечение отказоустойчивости

Для обеспечения отказоустойчивости используем принцип **N+1**, предполагающий наличие ресурсов для восстановления необходимого количества реплик при отказе одной рабочей ноды.

Выберем четыре Worker Nodes с характеристиками 8 vCPU и 16 ГБ RAM каждая.

Общие ресурсы рабочих нод:

- CPU: 4 × 8 = 32 vCPU.
- RAM: 4 × 16 = 64 ГБ.

После отказа одной рабочей ноды останутся три узла:

- CPU: 3 × 8 = 24 vCPU.
- RAM: 3 × 16 = 48 ГБ.

Суммарных физических ресурсов достаточно для размещения приложения, которому необходимо 17 CPU и 30,25 ГБ RAM.

Для базы данных и системы кеширования предусмотрено по три реплики. Чтобы избежать размещения нескольких реплик одного компонента на одной ноде, предполагается использование механизмов `podAntiAffinity` или `topologySpreadConstraints`.

Наличие трёх реплик само по себе не гарантирует отказоустойчивость данных. Для реальной эксплуатации также необходимы механизмы репликации, постоянное хранилище и восстановление после сбоев.

### 4. Расчёт служебных ресурсов Kubernetes

Не все ресурсы рабочих нод доступны для размещения приложений. Часть ресурсов необходима операционной системе и компонентам Kubernetes.

Для учебного расчёта примем следующие служебные резервы на одну Worker Node:

| Назначение | CPU | RAM |
|---|---:|---:|
| Операционная система | 0,3 | 0,5 ГБ |
| Компоненты Kubernetes | 0,3 | 0,5 ГБ |
| Резерв для предотвращения eviction | 0 | 0,5 ГБ |
| **Итого** | **0,6** | **1,5 ГБ** |

Это расчётные допущения, поскольку конкретные значения служебных резервов в условии задания не указаны.

Доступные ресурсы одной рабочей ноды:

- CPU: 8 − 0,6 = **7,4 CPU**.
- RAM: 16 − 1,5 = **14,5 ГБ**.

В реальном кластере доступные ресурсы определяются настройками `kubeReserved`, `systemReserved`, `evictionHard`, а также запросами ресурсов системных Pod.

### 5. Проверка отказоустойчивости с учётом служебных ресурсов

После отказа одной Worker Node остаются три рабочих узла.

| Показатель | CPU | RAM |
|---|---:|---:|
| Физические ресурсы | 24 | 48 ГБ |
| Служебные резервы | 1,8 | 4,5 ГБ |
| Доступно приложению | 22,2 | 43,5 ГБ |
| Потребность приложения | 17 | 30,25 ГБ |
| **Свободный резерв** | **5,2** | **13,25 ГБ** |

Проверим пример размещения всех реплик на трёх оставшихся нодах:

| Нода | DB | Cache | Frontend | Backend | CPU | RAM |
|---|---:|---:|---:|---:|---:|---:|
| Worker 1 | 1 | 1 | 2 | 3 | 5,4 | 9,9 ГБ |
| Worker 2 | 1 | 1 | 2 | 3 | 5,4 | 9,9 ГБ |
| Worker 3 | 1 | 1 | 1 | 4 | 6,2 | 10,45 ГБ |
| **Итого** | **3** | **3** | **5** | **10** | **17** | **30,25 ГБ** |

Все три рабочие ноды укладываются в доступные ресурсы 7,4 CPU и 14,5 ГБ RAM на узел.

Таким образом, выбранная конфигурация позволяет разместить необходимое количество реплик после отказа одной рабочей ноды.

### 6. Расчёт управляющих нод Control Plane

Помимо рабочих нод, кластер Kubernetes содержит управляющие компоненты:

- `kube-apiserver` — предоставляет Kubernetes API.
- `kube-scheduler` — отвечает за планирование размещения Pod.
- `kube-controller-manager` — управляет состоянием ресурсов кластера.
- `etcd` — хранит состояние Kubernetes-кластера.

Для обеспечения отказоустойчивости управляющего слоя предлагается использовать три отдельные Control Plane Nodes.

В качестве предварительной конфигурации принимаем:

- Количество: 3 ноды.
- CPU: 2 vCPU на ноду.
- RAM: 4 ГБ на ноду.

При использовании трёх участников etcd кластер сохраняет кворум при отказе одного из них. Для сохранения доступности Kubernetes API также требуется отказоустойчивая точка доступа к API-серверам.

Параметры Control Plane являются оценочными и зависят от размера кластера и нагрузки.

### 7. Использование Helm

По условию задания приложение должно быть пригодно для развёртывания в разных окружениях с помощью Helm.

Для этого предполагается создание Helm-чарта, содержащего шаблоны Kubernetes-ресурсов для базы данных, кеша, фронтенда и бекенда.

Параметры, которые могут отличаться между окружениями, выносятся в `values.yaml`:

- Количество реплик компонентов.
- Запросы и ограничения ресурсов (`requests` и `limits`).
- Настройки контейнерных образов.
- Параметры хранения данных.
- Настройки сетевого доступа.
- Правила распределения Pod между нодами.

Для отдельных окружений могут использоваться файлы `values-dev.yaml`, `values-test.yaml` и `values-prod.yaml`.

Это позволяет применять единые шаблоны Kubernetes-ресурсов, изменяя конфигурацию приложения без дублирования манифестов.

Практическое создание Helm-чарта не входит в расчётную часть данного задания.

### 8. Итоговая конфигурация Kubernetes-кластера

По результатам расчётов предлагается следующая архитектура:

| Тип узла | Количество | CPU на узел | RAM на узел | CPU всего | RAM всего |
|---|---:|---:|---:|---:|---:|
| Control Plane | 3 | 2 vCPU | 4 ГБ | 6 | 12 ГБ |
| Worker Node | 4 | 8 vCPU | 16 ГБ | 32 | 64 ГБ |
| **Итого** | **7** | | | **38 vCPU** | **76 ГБ** |

**Вывод:**

Для размещения приложения предлагается Kubernetes-кластер из семи нод: трёх Control Plane и четырёх Worker Nodes.

Выбранная конфигурация обеспечивает:

- Достаточные вычислительные ресурсы для размещения 21 реплики приложения.
- Резерв CPU и оперативной памяти для восстановления реплик после отказа одной рабочей ноды.
- Возможность распределения реплик базы данных и кеша по разным рабочим узлам.
- Отказоустойчивость управляющего слоя при корректной настройке etcd и доступа к Kubernetes API.
- Возможность параметризации развёртывания приложения для разных окружений с помощью Helm.

Расчёт учитывает CPU и RAM. Для реальной эксплуатации дополнительно потребуется определить требования к дисковому пространству, производительности хранилища, сети и механизмам репликации данных.
