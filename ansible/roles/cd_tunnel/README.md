# cd_tunnel — проект, без активации

Роль намеренно НЕ создаёт доступ и НЕ готова к применению в production.
Она проверяет явно переданный публичный ключ и готовит root-owned кандидаты
в /var/lib/cd-tunnel-review (0700), вне /etc/ssh. По умолчанию останавливается
assert: cd_tunnel_stage_review_approved=false. Нет handlers, reload/restart,
изменений cloud-init, sudo или административных ключей ubuntu.

## Будущая подготовка (не выполнялась)

После отдельного разрешения на staging передать cd_tunnel_public_key как одну
строку публичного ключа без options и переводов строк, и явно включить
cd_tunnel_stage_review_approved. Нет реального ключа в defaults/примере.
Формат сначала проверяет assert, затем ssh-keygen -l -f (только чтение,
не генерация). no_log скрывает ключ и диагностику. Шаблоны создаются только
после успешного разбора. Пример playbook: ansible/cd-tunnel-review.yml.
Не передавать ключ через публичные логи или историю shell.
Все операции записи и cleanup наследуют block-level when:
cd_tunnel_stage_review_approved | bool и not ansible_check_mode. Поэтому
--start-at-task внутри блока не позволяет писать файлы при выключенном gate.
Начальный assert также даёт понятную ошибку при обычном запуске без разрешения.
Это защита от случайного запуска, не от оператора, меняющего playbook/vars.

После создания review-каталога READY.json удаляется ДО проверки нового ключа.
Он создаётся последним только после разбора ключа, записи обоих кандидатов и
расчёта SHA256: JSON-массив содержит хеши authorized_keys, затем sshd-match.conf.
Без маркера комплект НЕ готов, даже если остались старые файлы. Перед любым
ручным использованием нужно сверить оба хеша с маркером. Это маркер готовности
review-файлов, не доказательство серверной совместимости или разрешение активации.
Ошибка до инвалидирования (например, недоступный сервер) не является началом
новой проверки; прежний маркер относится только к прежнему комплекту.
После инвалидирования сбой оставляет комплект неготовым. Прерванный запуск не
возобновлять с --start-at-task: при включённом gate всегда повторять целиком.
Параллельные staging-запуски запрещены организационно: блокировки в проекте нет.
Временный validation-файл удаляется always при обычной обработке ошибок, но
аварийное прекращение процесса/связи может прервать cleanup.
Повторное staging даёт те же кандидаты, но временный файл и маркер отмечают changes.
В check mode весь блок записи пропускается: это не полная проверка.

## Гейт активации: отдельный будущий проект и подтверждение

Не копировать кандидат в активный sshd автоматически. Облако выключено,
фактическая конфигурация неизвестна. Перед созданием пользователя и интеграцией
потребуется отдельное разрешение, новая проверенная доработка роли и:

1. Проверить версию OpenSSH Ubuntu 22.04, поддержку restrict/port-forwarding,
   permitopen, MaxSessions и всех Match directives. Изучить действующие
   /etc/ssh/sshd_config, Include и /etc/ssh/sshd_config.d/*.conf, PAM, AllowUsers,
   группы и sudoers. Не считать sshd_config.d автоматически подключённым.
2. Сохранить рабочий административный доступ ubuntu, резервную сессию и консоль,
   копию конфигурации и план отката. Не менять глобальные настройки SSH.
   Определить место отдельного Match User в реально действующей конфигурации:
   он не должен попадать внутрь чужого Match или перехватываться более ранними
   применимыми правилами. Match all в конце остаётся контекстом Match и НЕ возвращает глобальный
   контекст; он не устраняет конфликты порядка. Глобальные директивы после Include с Match могут
   стать недопустимыми: требуется проверка всей собранной конфигурации.
3. Создать cd-tunnel без sudo/привилегированных групп и парольного входа;
   серверное AuthenticationMethods publickey обязательно. Проверить влияние
   блокировки пароля на pubkey/PAM. Планируемая shell /bin/sh не даёт доступ
   к командам при эффективном MaxSessions 0; shell/exec/SFTP закрываются sshd,
   ключ дополнительно использует command=/bin/false. nologin не выбирается:
   совместимость с ssh -N и PAM не доказана. Учётная запись только для SSH,
   без иных способов входа; отдельно проверить локальные политики.
4. После проверки поместить единственный ограниченный ключ в root-owned
   /etc/ssh/authorized_keys/cd-tunnel, не меняя ubuntu. Проверить чтение файла
   фактическим sshd в контексте целевого пользователя и StrictModes. Нельзя
   считать root-owned 0600 рабочим режимом активного файла без этой проверки.
   Возможны root:root 0644 (публичный ключ) либо root-owned 0640 с отдельной
   группой чтения и подходящим проходом по каталогам; запись CI запрещена.
   Точные права и владельцы согласуются после проверки сервера. Review-файлы
   остаются root-owned 0600 в каталоге 0700, так как sshd их не читает. Пользователь не должен менять свой файл ключей. Стандартный домашний
   authorized_keys для него не используется. Роль сейчас НЕ создаёт этот путь.
5. До reload проверить /usr/sbin/sshd -t на полной конфигурации. Сравнить
   /usr/sbin/sshd -T -C user=cd-tunnel,host=RUNNER_HOST,addr=RUNNER_IP и аналогично
   user=ubuntu с действительным адресом администратора. Подставлять реальные
   параметры только в согласованной серверной проверке; не полагаться на
   изолированный sshd -t -f шаблона. Проверить AuthorizedKeysFile, publickey,
   отсутствие password/keyboard-interactive, local-only TCP forwarding,
   PermitOpen 127.0.0.1:6443, MaxSessions 0 и прочие запреты. Эффективные параметры
   ubuntu должны сохранить административный доступ. До этого reload запрещён.
6. Только по осознанному отдельному решению выполнить reload, не restart,
   сохраняя административную сессию и возможность немедленного отката.
   Автоматический handler намеренно отсутствует.
7. После отдельного разрешения выполнить положительную проверку ssh -N -T
   и API через loopback, отрицательные проверки команд/PTY/SFTP, -R,
   agent/X11, других назначений. Запрет назначений проверять реальным открытием
   канала, а не одним созданием локального listener. PermitOpen не ограничивает
   адрес bind на runner; workflow обязан слушать 127.0.0.1.

## Остальные условия

Доверенный host key, CA/TLS SAN API, ограниченный Kubernetes ServiceAccount,
ротация SSH-ключа/токена и безопасное хранение GitHub Secrets требуют отдельного
разрешения. Не использовать admin.conf и административный SSH-ключ.
Роль не меняет firewall, SG, Kubernetes, GitHub или workflow. CD остаётся false &&.
Фоновые туннели и любые серверные проверки сейчас не разрешены.

## Статическая проверка

Из ansible/: ansible-playbook -i 'localhost,' cd-tunnel-review.yml --syntax-check.
Без выполнения playbook inventory не подключается к ВМ; ключ для syntax-check
не нужен. Затем ansible-lint cd-tunnel-review.yml roles/cd_tunnel, если установлен.
Эти проверки не заменяют серверные sshd -t/-T и проверку administrative access.
